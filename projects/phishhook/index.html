Case study 01Authorized awareness engineering

PhishHook

A consent-based training tool designed to make phishing-awareness campaigns reviewable, measurable, and deliberately limited.

Python 3.12+CustomTkinterCloudflare WorkersD1SQLiteSMTP
The problem

Awareness training needs boundaries as much as it needs measurement.

PhishHook is a local-first desktop application for explicitly authorized phishing-awareness exercises. It supports a structured path from campaign review to sending and then to interpretation of anonymous link-interaction signals.

The project deliberately avoids credential collection and arbitrary form data. It is designed for small portfolio demonstrations and controlled training-not unattended bulk email or production monitoring.

Review the source on GitHub ↗
System flow

Desktop control, small public signal service.

ReviewApproveSendInterpret

The desktop side manages campaigns, SMTP configuration, local SQLite records, and the visual dashboard. A small TypeScript Cloudflare Worker records anonymous interaction events in D1 and exposes them to the authorized desktop client.

Campaign confirmation

A final review step helps prevent accidental sending. The application keeps a deliberate 25-recipient cap and requires the operator to supply an authorized SMTP account.

Dashboard

The live interface combines campaign history, a proportional engagement funnel, recipient state, a 24-hour signal ribbon, scanner-aware classifications, send-failure summaries, and an event table using local Tkinter Canvas primitives.

Interpretation

A signal is evidence-not a conclusion.

SMTP acceptance is not proof of delivery. A raw tracking hit may be an automated mail scanner rather than a person.

PhishHook keeps these caveats visible because email infrastructure can create misleading signals. The project’s scanner-aware classifications help an operator distinguish raw events from defensible interpretations.

  • No passwords or credentials are collected.
  • No arbitrary form submissions are collected.
  • Screenshots use synthetic demo data.
  • Secrets are supplied at runtime and should never be committed.
  • The education page directs users to an official phishing-prevention resource.
Testing & limits

Useful because its limits are stated.

The desktop application can run in demo mode without a Worker or CustomTkinter, while real sending requires both an authorized account and a deployed Worker. Automated tests are run with pytest, and the repository includes a Windows packaging workflow.

The current Worker is intended for small demonstrations. Free-tier service limits may change, and the system is not presented as a complete enterprise awareness platform.

Future direction

Further work could deepen delivery-state explanation, expand scanner classification, improve campaign comparison, and add additional privacy-preserving export formats-without changing the project’s consent-first scope.
